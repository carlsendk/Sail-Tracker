### Goal

Create a skeleton `deploy-prod.yml` workflow and a release-process doc that establish `merge to main` as the single promotion rule for production deployments, and wire `workflow_dispatch` for emergency redeploys.

### Context

There is no production deployment workflow in the repository today. Vercel currently auto-deploys on every push to `main` via its native Git integration, with no coordination with Supabase migrations. This issue creates the workflow skeleton that Phase 4 issues #34–#37 will populate with jobs (`validate`, `migrate`, `smoke`, `deploy`). The skeleton itself does nothing beyond defining the trigger; it establishes the file that subsequent issues extend and documents the promotion rule so every contributor knows what "releasing" means for this project.

### Embedded Spec

From `docs/plans/plan.md` § Phase 4 → Scope:

> - define the promotion rule, likely merge to `main`

From `docs/plans/plan.md` § Phase 4 → Success condition:

> a production release updates both Supabase and Vercel in the correct order with clear failure boundaries

### Files

- Create: `.github/workflows/deploy-prod.yml` — skeleton with `on: push: branches: [main]` and `on: workflow_dispatch`. Jobs section left as a placeholder comment; actual jobs added by #34–#37.
- Create: `docs/development/release-process.md` — documents the promotion rule, explains what triggers production deployment, and notes that manual `workflow_dispatch` is available for emergency redeploys.

`.github/workflows/deploy-prod.yml` initial skeleton shape:

```yaml
name: Deploy to Production

on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      reason:
        description: "Reason for manual redeploy"
        required: false

# Jobs added by #34 (validate), #35 (migrate), #36 (smoke), #37 (deploy)
jobs: {}
```

Note: `jobs: {}` is a valid YAML placeholder but an invalid GitHub Actions workflow (no runnable job). The PR for this issue should document that the skeleton is intentionally inert until #34 adds the first real job.
