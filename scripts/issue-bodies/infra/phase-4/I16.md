### Goal

Add a `smoke` job to `deploy-prod.yml` that runs a small set of read-only assertions against the production Supabase database immediately after migrations apply, blocking the Vercel deploy if any assertion fails.

### Context

Applying migrations is not sufficient to confirm the production database is healthy. A migration can succeed syntactically but leave the schema in an inconsistent state for the application. The `smoke` job runs after `migrate` and before the Vercel `deploy` job (#37), providing a fast sanity check without touching application traffic. The check script (`scripts/prod-smoke.mjs`) connects to the production Supabase using the service-role key and runs read-only queries: confirm expected tables exist, confirm `tenants` has at least one row, and any other lightweight assertions the implementer deems appropriate. If any assertion fails, the job exits non-zero and the `deploy` job never runs.

**Prerequisite secrets** — the following GitHub Actions secrets must be set by an operator before this job can run:

- `SUPABASE_ACCESS_TOKEN` — already required by #35
- `SUPABASE_PROD_PROJECT_REF` — already required by #35; used here to derive the production Supabase URL
- A production service-role key (e.g., `SUPABASE_PROD_SERVICE_ROLE_KEY`) for the smoke script to authenticate read-only queries

If the production URL and service-role key can be derived from existing secrets (e.g., via the Supabase management API using `SUPABASE_ACCESS_TOKEN` + `SUPABASE_PROD_PROJECT_REF`), the implementer may avoid adding a new secret. Document the chosen approach in the PR.

### Files

- Modify: `.github/workflows/deploy-prod.yml` — add `smoke` job with `needs: migrate`; runs `node scripts/prod-smoke.mjs`.
- Create: `scripts/prod-smoke.mjs` — lightweight Node script using the Supabase JS client or raw `fetch` to verify: (a) the `tenants` table exists and has at least one row, (b) a small set of other critical tables are reachable (implementer to define based on current schema). Script exits 0 on pass, non-zero on any failure.

`smoke` job shape in `deploy-prod.yml`:

```yaml
  smoke:
    needs: migrate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Install dependencies
        run: pnpm install --frozen-lockfile
      - name: Run production smoke check
        run: node scripts/prod-smoke.mjs
        env:
          SUPABASE_URL: ${{ secrets.SUPABASE_PROD_URL }}
          SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.SUPABASE_PROD_SERVICE_ROLE_KEY }}
```

### TDD Steps

1. Create `scripts/prod-smoke.mjs` with the assertions listed above. Run it locally against the development Supabase project (with a dev `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `.env`) — expect PASS.
2. Temporarily comment out the `tenants` table insert in a local `db reset` to simulate an empty table. Re-run the smoke script — expect FAIL on the row-count assertion.
3. Restore the seed. Add the `smoke` job to `deploy-prod.yml` on a test branch. Push.
4. Observe GitHub Actions: with real production secrets set, `smoke` should pass after `migrate`. Confirm `deploy` is still skipped (#37 not yet implemented).
5. Temporarily introduce a bogus assertion (e.g., assert a table name that does not exist) in the test branch. Push — expect `smoke` to fail; confirm `deploy` shows as skipped.
6. Revert the bogus assertion and push again — expect PASS.
7. Remove the test branch. Commit `chore(infra): add post-migration smoke check job`.
