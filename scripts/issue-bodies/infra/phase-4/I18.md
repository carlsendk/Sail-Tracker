### Goal

Document rollback expectations for three failure scenarios in the production deployment pipeline: a failed Supabase migration mid-deploy, a successful migration followed by a failed Vercel deploy, and a successful deploy followed by a post-deploy regression.

### Context

Once #35 (migrate) and #37 (deploy) are merged, on-call responders need a clear runbook for what to do when the pipeline breaks. Supabase migrations are generally irreversible once applied to production — a rollback is a forward migration, not an undo. Vercel deploys can be rolled back quickly via the Vercel dashboard or CLI. This issue documents what is reversible, what is not, and what the prevention for each scenario is. The audience is a developer on call at 2am who has never read this document before.

### Files

- Modify: `docs/development/release-process.md` — add a "Rollback" section covering the three scenarios below. The section should be self-contained enough to use as a runbook without reading the rest of the document.

**Three scenarios to cover:**

1. **Failed Supabase migration mid-deploy** (`migrate` job fails): The pipeline stops before Vercel deploys. The database may be in a partially applied state if `supabase db push` applies migrations transactionally on failure; document whether `supabase db push` rolls back on error or leaves partial state (check Supabase CLI docs during authoring). On-call action: inspect the Supabase dashboard migration history; if partial, write and apply a forward-only corrective migration; do not attempt to reverse applied SQL manually.

2. **Successful migration, failed Vercel deploy** (`migrate` passes, `deploy` fails): The database schema is ahead of the deployed application. On-call action: fix the Vercel deploy failure (check build logs, secrets, environment variables) and re-trigger `workflow_dispatch` — the `migrate` job will report "no migrations to apply" and the `deploy` job will proceed. If the application cannot serve traffic safely with the new schema and old code, assess whether to route traffic to the previous Vercel deployment (instant rollback via Vercel dashboard → Deployments → Promote) while the fix is prepared.

3. **Successful deploy, post-deploy regression** (pipeline passes but the running app has a bug): On-call action: immediately promote the previous Vercel deployment to production via the Vercel dashboard. Database changes from the same release remain applied; assess whether the previous code version is compatible with the new schema before promoting. If not, a forward migration to restore compatibility is required before promoting the old Vercel build.

For each scenario, the doc must state: what the on-call can do, what they cannot easily undo, and what the prevention is (e.g., smoke check, staging environment, feature flags).
