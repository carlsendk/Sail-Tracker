### Goal

Add a `deploy` job to `deploy-prod.yml` that promotes the latest commit to Vercel production using the Vercel CLI, and ensure this workflow — not Vercel's native Git integration — is the single source of truth for production deployments.

### Context

After `migrate` (#35) and `smoke` (#36) succeed, the deploy job pushes the web app to Vercel production. Vercel currently auto-deploys on every push to `main` via its native Git integration. Once this job is working, that native integration should be disabled so database migrations always precede the web deploy and a failed migration cannot result in a deployed app backed by an incompatible schema. The primary approach is the Vercel CLI (`vercel --prod`) authenticated with `VERCEL_TOKEN`; an alternative is the Vercel Deployments REST API. Implementer should evaluate both and document the chosen approach in the PR.

**Prerequisite secrets** — the following GitHub Actions secrets must be set by an operator before this job can run:

- `VERCEL_TOKEN` — Vercel personal access token with deploy permission for the project
- `VERCEL_PROJECT_ID` — the Vercel project ID (found in Vercel project settings)
- `VERCEL_ORG_ID` — the Vercel team/org ID

### Files

- Modify: `.github/workflows/deploy-prod.yml` — add `deploy` job with `needs: [migrate, smoke]`; uses Vercel CLI to trigger a production deployment.
- Modify (conditional): `vercel.json` — may need to set `"github": { "enabled": false }` to disable Vercel's native Git integration. Evaluate during implementation; if the native integration is disabled, document it here and in `docs/development/release-process.md`.

`deploy` job shape in `deploy-prod.yml`:

```yaml
  deploy:
    needs: [migrate, smoke]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Vercel production
        run: npx vercel --prod --token ${{ secrets.VERCEL_TOKEN }} --yes
        env:
          VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
          VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}
```

Note: `npx vercel --prod` deploys the current commit. If the project uses a build step separate from Vercel's build system, `vercel build` followed by `vercel deploy --prebuilt` may be preferable. Document the chosen approach in the PR.

### TDD Steps

1. Confirm `VERCEL_TOKEN`, `VERCEL_PROJECT_ID`, and `VERCEL_ORG_ID` are present in the repository's Actions secrets.
2. Add the `deploy` job to `deploy-prod.yml` on a test branch. Push. Observe GitHub Actions — with `migrate` and `smoke` not yet passing on the test branch (no production secrets), confirm the `deploy` job shows as skipped.
3. On a branch where `migrate` and `smoke` are simulated as passing (or with real production secrets), trigger `workflow_dispatch` from the GitHub Actions UI. Expect the `deploy` job to run and produce a Vercel deployment URL in the logs.
4. Confirm the Vercel deployment URL resolves in a browser and shows the correct application version.
5. Simulate a `smoke` failure (temporary bogus assertion per #36 TDD Steps). Push. Expect `deploy` to be skipped.
6. Decide whether to disable Vercel's native Git integration. If yes, set `"github": { "enabled": false }` in `vercel.json` and verify that a push to `main` no longer triggers a Vercel auto-deploy outside of this workflow.
7. Commit `chore(infra): add vercel production deploy job`.
