### Goal

Add a `migrate` job to `deploy-prod.yml` that applies pending Supabase migrations to the production project using the Supabase CLI, hard-failing the deploy if any migration step errors.

### Context

This is the first job in `deploy-prod.yml` that touches production infrastructure. It depends on `validate` (#34) — so CI must be green — and on #31 (database validation in CI), which proves migrations apply cleanly in a controlled environment before this job ever runs them remotely. The job uses `supabase db push` with a project reference and access token to push pending local migrations to the Supabase cloud project. If `supabase db push` exits non-zero, the job fails immediately and the Vercel deploy job (#37) never runs.

**Prerequisite secrets** — the following GitHub Actions secrets must be set by an operator before this workflow can run:

- `SUPABASE_ACCESS_TOKEN` — personal access token with migration push permission
- `SUPABASE_PROD_PROJECT_REF` — the production Supabase project reference (found in the Supabase dashboard URL)

These secrets are not created by this issue. The implementer should verify they exist in the repository's Actions secrets before merging.

### Files

- Modify: `.github/workflows/deploy-prod.yml` — add `migrate` job with `needs: validate`; uses Supabase CLI to run `supabase db push` against the production project ref.
- Modify: `docs/development/release-process.md` — extend with a "Migration Step" section explaining what `supabase db push` does, which secrets it requires, and what happens when it fails.

`migrate` job shape in `deploy-prod.yml`:

```yaml
  migrate:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
        with:
          version: latest
      - name: Apply migrations to production
        run: supabase db push --project-ref ${{ secrets.SUPABASE_PROD_PROJECT_REF }}
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
```

### TDD Steps

2. Add the `migrate` job to `deploy-prod.yml` on a test branch. Push without the secrets set (use a fork or a secrets-less environment if available). Expect the job to fail with a "secret not found" or auth error — confirm failure is clean and does not leave migrations in a partial state.
3. Set the secrets. Push again. Expect `supabase db push` to run and either apply pending migrations (if any) or report "no migrations to apply" and exit 0.
4. Temporarily corrupt a migration file in the test branch (add invalid SQL). Push. Expect the `migrate` job to fail; confirm `smoke` and `deploy` jobs show as skipped in the Actions UI.
5. Revert the corruption. Run again — expect PASS.
6. Remove the test branch artifacts. Extend `docs/development/release-process.md`.
7. Commit `chore(infra): add supabase migration job to deploy-prod workflow`.
