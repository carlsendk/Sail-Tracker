### Goal

Document the canonical hosted environment contract and clean up `.env.example` so there is no ambiguity about which Supabase keys are expected when developing against a hosted project.

### Context

The repository currently has four Supabase-related env vars in `.env.example`, with contradictory comments: `SUPABASE_SERVICE_ROLE_KEY` is listed first and treated as canonical, while `SUPABASE_SECRET_KEY` is labeled "Legacy fallback". Phase 2 inverts this: `SUPABASE_SECRET_KEY` is the canonical secret-key name going forward (matching the Supabase dashboard's current naming, `sb_secret_...`), and `SUPABASE_SERVICE_ROLE_KEY` is the symbol being retired. This issue establishes that in documentation and cleans up the comments in `.env.example` to match — no code changes yet.

The hosted env contract covers three surfaces: the browser client (Next.js client components), server-side code (server actions, route handlers), and admin scripts (bootstrap).

### Embedded Spec

From `docs/plans/plan.md` § Phase 2:

> ## Phase 2: Environment Contract Cleanup
>
> Make environment handling explicit for both hosted and local modes.
>
> Scope:
>
> - define the hosted env contract using `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY`
> - define the local env contract using CLI-provided local credentials where required
> - add a small resolver layer so the app and bootstrap logic can choose the correct key set by environment
> - remove unnecessary legacy fallbacks once the supported local path is clear
>
> Success condition:
>
> - there is one documented env contract for hosted development and one for local development, with no ambiguity about which keys are expected

### Files

- Create: `docs/development/env-contract.md` — primary deliverable; hosted contract section only (local section added by #26)
- Modify: `.env.example` — update comments to remove "Legacy fallback" language; rename `SUPABASE_SERVICE_ROLE_KEY` to `SUPABASE_SECRET_KEY` (single canonical name) and drop the duplicate entry

`docs/development/env-contract.md` should cover:

1. Variable table for hosted mode:

   | Variable | Surface | Notes |
   |---|---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | browser, server, scripts | Project URL from Supabase Connect dialog |
   | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | browser only | Anon/publishable key; safe to expose; RLS must be in place |
   | `SUPABASE_SECRET_KEY` | server, scripts | `sb_secret_...` from Settings → API Keys; never shipped to the browser |
   | `PLATFORM_ADMIN_EMAIL` | scripts | Email for the bootstrap platform admin account |

2. Which surfaces read which key and why (browser cannot read `SUPABASE_SECRET_KEY`; server actions and route handlers must not use the publishable key for admin operations).

3. A note that `SUPABASE_SERVICE_ROLE_KEY` was the previous name for the secret key and is being retired; code that still reads it will be removed in #28.

### TDD Steps

This is a docs issue. Use the "follow the doc on a clean checkout" pattern:

1. Verify the current `.env.example` ambiguity: confirm both `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_SECRET_KEY` entries exist and that the comments call one "Legacy fallback".

6. Copy `.env.example` to a scratch `.env` and confirm `SUPABASE_SECRET_KEY` is the only secret-key entry.
7. Commit `docs(infra): document hosted env contract`.
