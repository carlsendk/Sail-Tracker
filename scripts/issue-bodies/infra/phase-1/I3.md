### Goal

Extend `docs/development/local-supabase.md` with a migrations-and-seed section so developers understand what `pnpm supabase:reset` actually does to the database and what state to expect afterward.

### Context

`pnpm supabase:reset` runs `supabase db reset`, which applies every file in `supabase/migrations/` in filename order and then executes `supabase/seed.sql`. Without documentation, developers don't know whether they need to run additional steps after a reset, why a table might not exist, or how to add a new migration. This issue closes that gap with a focused reference section in the existing doc created by #22.

### Embedded Spec

From `docs/plans/plan.md` § Phase 1 → Scope:

From `docs/plans/plan.md` § Phase 1 → Success condition:

### Acceptance Criteria

- [ ] The "Migrations and seed data" section explains that `pnpm supabase:reset` drops and recreates the local DB, runs all files in `supabase/migrations/` in alphabetical order, then runs `supabase/seed.sql`
- [ ] The doc states the migration file naming convention: `YYYYMMDDNNNN_<description>.sql`
- [ ] The doc explains how to create a new migration: `supabase migration new <name>` generates a numbered file in `supabase/migrations/`
- [ ] The doc explains that `supabase/seed.sql` is auto-applied on every `reset` — edits to seed.sql take effect on the next `pnpm supabase:reset`
- [ ] The doc notes what a developer should see after a clean reset before bootstrap: the schema tables exist, but application-level data (tenants, profiles, roles) comes from `pnpm bootstrap:supabase` (documented in #24)
- [ ] `pnpm validate` passes
