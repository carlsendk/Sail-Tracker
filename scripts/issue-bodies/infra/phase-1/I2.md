### Goal

Write the local-ports-and-Studio section of `docs/development/local-supabase.md` so a developer knows where every local service lives and how to open the database GUI without reading CLI output.

### Context

Once `pnpm supabase:start` is available (#21), developers need a stable reference for which port maps to which service. Without it, they either run `supabase status` every time or accidentally point the app at the wrong URL. This is a pure-docs issue — no code changes.

### Embedded Spec

From `docs/plans/plan.md` § Phase 1 → Scope:

> - document the local ports and local Studio usage

From `docs/plans/plan.md` § Phase 1 → Success condition:

> a new developer can start local Supabase, reset the database, bootstrap baseline data, and run the web app without pointing at a hosted project

### Files

- Create: `docs/development/local-supabase.md` — new file; this issue owns the initial scaffold and the ports + Studio section. #23 and #24 will extend it with migrations and the full dev loop respectively.

The ports are taken from `supabase/config.toml` (source of truth):

| Service | Port |
|---------|------|
| REST API (`NEXT_PUBLIC_SUPABASE_URL`) | 54321 |
| PostgreSQL direct connection | 54322 |
| Studio (web UI) | 54323 |

Inbucket is not enabled in `supabase/config.toml` — omit it.

### Acceptance Criteria

- [ ] `docs/development/local-supabase.md` exists and has a "Local ports" table listing API (54321), DB (54322), and Studio (54323)
- [ ] The doc explains how to open Studio: navigate to `http://localhost:54323` after `pnpm supabase:start`
- [ ] The doc covers the most common port-conflict troubleshooting step: check what is listening on the conflicting port (`lsof -i :<port>`) and stop or remap as needed
- [ ] Port numbers match exactly what is in `supabase/config.toml` — no invented values
- [ ] The doc cross-references `pnpm supabase:start` and `pnpm supabase:stop` by exact script name
- [ ] `pnpm validate` passes (markdownlint / cspell if enabled, otherwise no regression)
