### Goal

Add a CI step that verifies migrations applied cleanly to the fresh local database started by #30 and that `seed.sql` populated the expected baseline rows, failing the job if either is absent or contradictory.

### Context

This is the third task in Phase 3 (Database Validation In CI). It builds on #30 (local Supabase running in CI) and #23 (Phase 1 — the documented migration application path). `supabase start` already auto-applies every file in `supabase/migrations/` and runs `supabase/seed.sql` when the stack comes up. This issue is therefore a **verification gate**, not a re-run of migrations: it adds a small Node script (`scripts/verify-migrations.mjs`) that performs one or more `SELECT` queries against known seeded tables and exits non-zero if the expected rows are absent. This gives CI a crisp, attributable failure when a migration is broken or a seed row was accidentally deleted, rather than surfacing the problem only when application tests fail with a cryptic Postgres error.

### Embedded Spec

From `docs/plans/plan.md` § Phase 3 → Scope:

> - run migrations and seed data on a fresh local database

Success condition from the same section:

> CI fails if migrations, seed data, bootstrap, or database-dependent app behavior are broken

### Files

- Create: `scripts/verify-migrations.mjs` — a short Node ESM script that connects to the local Supabase Postgres (using the `DATABASE_URL` env var printed by `supabase status`) and runs a minimal SELECT against at least one seeded table; exits `1` if the row count is zero or the query throws
- Modify: `.github/workflows/ci.yml` — add a step that captures `DATABASE_URL` from `supabase status` and invokes `node scripts/verify-migrations.mjs`

### Acceptance Criteria

- [ ] `scripts/verify-migrations.mjs` exists and connects to the local Postgres URL supplied via the `DATABASE_URL` environment variable
- [ ] The script performs at minimum one `SELECT count(*) FROM <known-seeded-table>` and exits non-zero when the count is 0 or the query fails
- [ ] `.github/workflows/ci.yml` has a step `name: Verify migrations and seed` placed after `Wait for Supabase DB ready` (from #30) and before `Lint`
- [ ] The step exports `DATABASE_URL` from `supabase status --output env` (or equivalent) and passes it to the script
- [ ] If `scripts/verify-migrations.mjs` exits non-zero, the job fails at that step — not silently absorbed
- [ ] A broken migration (e.g. a file with invalid SQL temporarily added) causes this step to fail before any application test runs
- [ ] A seed file with a missing INSERT for the verified table causes this step to fail with an explicit message (the script should print which table had zero rows)

### TDD Steps

Two parallel TDD tracks — the script and the workflow step:

**Script track (traditional TDD):**
1. Write a failing test in `scripts/verify-migrations.test.mjs` (or Vitest spec) that imports `verify-migrations.mjs` and asserts it calls `process.exit(1)` when the query returns count 0. Run → FAIL (script does not exist).
2. Implement `verify-migrations.mjs` with the minimal SELECT and exit logic. Run test → PASS.
3. Run `node scripts/verify-migrations.mjs` locally against a running `supabase start` instance. Confirm exit 0. Then empty the seeded table in a local psql session and re-run. Confirm exit 1 with an explanatory message.

**Workflow step track (Actions validation):**
1. On a feature branch, add the `Verify migrations and seed` step with the script call. Push. Observe the Actions run — expect PASS (the local DB has valid seed data).
2. Temporarily corrupt `supabase/seed.sql` (e.g. comment out the INSERT for the verified table) and push. Observe the job fail at exactly this step, not at a later test step.
3. Restore `seed.sql`. Push. Confirm the step passes and downstream steps are unaffected.
