### Goal

Run a DB-backed Vitest test suite against the live local Supabase instance started by #30/#31 in CI, surfacing database-dependent application behaviour failures before any production deployment.

### Context

This is the fourth and final task in Phase 3 (Database Validation In CI). The existing test suite (`apps/web/tests/`) has 9 unit-level tests — all resolve configuration or mock Supabase I/O; none hit a real Postgres instance. This issue adds a new test project (`apps/web/tests/db/`) that performs actual DB reads/writes against the local Supabase instance, then wires that project into CI as a separate `Test (DB)` step that runs after `Verify migrations and seed`. The "L" sizing reflects that connecting live tests to a real DB typically surfaces test-isolation failures (shared state between tests), ordering dependencies, or hard-coded assumptions about mock data that must be resolved before the suite can be clean. Both the unit test suite and the DB-backed suite continue to pass in CI independently.

### Embedded Spec

From `docs/plans/plan.md` § Phase 3 → Scope:

> - execute application checks against that database-backed environment

Success condition from the same section:

> CI fails if migrations, seed data, bootstrap, or database-dependent app behavior are broken

### Files

- Create: `apps/web/tests/db/` — directory for DB-backed specs (start with at least one smoke spec, e.g. `apps/web/tests/db/vessel-registry.db.test.ts`, that reads a seeded row from a known table)
- Create: `apps/web/vitest.config.db.ts` — a second Vitest config (or a `db` project entry in the existing `vitest.config.ts` projects array) that:
  - points `include` at `apps/web/tests/db/**/*.test.ts`
  - reads `DATABASE_URL` (or the individual Supabase env vars: `SUPABASE_URL`, `SUPABASE_ANON_KEY`) from the environment rather than `.env.local`
  - does **not** load the mock setup files used by the unit suite
- Modify: `.github/workflows/ci.yml` — add a step `name: Test (DB-backed)` that exports Supabase credentials from `supabase status --output env` and runs `pnpm vitest run --config apps/web/vitest.config.db.ts`; placed after `Verify migrations and seed` and before `Build`

**Recommended approach:** two separate Vitest configs (unit vs. DB) rather than an env flag that skips DB tests when the DB is absent. Reasons: cleaner separation between fast unit feedback and slower DB-backed checks; the unit config remains runnable offline; CI runs both in sequence with explicit step names so failures are attributed clearly.

### Acceptance Criteria

- [ ] `apps/web/tests/db/` directory exists with at least one spec that performs a real Supabase query (no mocks)
- [ ] `apps/web/vitest.config.db.ts` exists, includes only `tests/db/**`, and does not load mock setup files
- [ ] The DB spec reads at minimum one row from a seeded table and asserts expected field values (not just "truthy")
- [ ] Running `vitest run --config apps/web/vitest.config.db.ts` locally against a live `supabase start` instance passes
- [ ] Running `vitest run --config apps/web/vitest.config.db.ts` with no DB available fails with a connection error (not silently skipped)
- [ ] `.github/workflows/ci.yml` has step `name: Test (DB-backed)` positioned after `Verify migrations and seed` and before `Build`
- [ ] The existing `Test` step (unit suite) is unchanged and still passes without a DB
- [ ] Each DB-backed test cleans up any rows it inserts (use `afterEach` / `afterAll` teardown) so tests are order-independent
- [ ] CI run log shows both `Test` (unit) and `Test (DB-backed)` steps with independent pass/fail status

### TDD Steps

**DB spec track (traditional TDD):**
1. Write `apps/web/tests/db/vessel-registry.db.test.ts` with a test that calls the Supabase client (using `SUPABASE_URL` + `SUPABASE_ANON_KEY` from `process.env`) to fetch rows from a known seeded table and asserts at least one row exists. Run with `vitest run --config apps/web/vitest.config.db.ts` locally (without a running DB) → expect FAIL with a connection error.
2. Start `supabase start` locally (`pnpm supabase:start` from Phase 1). Re-run → expect FAIL (config file does not exist yet or seed table name is wrong). Fix the table reference and config path incrementally.
3. Once the spec passes against a live local DB, verify it fails again when you truncate the seeded table in a `psql` session. This confirms the assertion is meaningful, not vacuously truthy.
4. Add `afterEach` teardown for any rows inserted by the test. Confirm tests pass when run twice in sequence without a DB reset between runs.

**Workflow step track (Actions validation):**
1. Add the `Test (DB-backed)` step to `.github/workflows/ci.yml`. Push. Observe both `Test` and `Test (DB-backed)` pass on the Actions run.
2. Temporarily break the DB spec (assert a row count that cannot be true given the seed data). Push. Confirm only `Test (DB-backed)` fails; `Test` (unit) still passes.
3. Restore the spec. Push. Confirm both steps pass.
