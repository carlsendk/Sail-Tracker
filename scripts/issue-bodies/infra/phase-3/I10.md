### Goal

Add a `supabase start` step to `.github/workflows/ci.yml` that launches a local Supabase stack on the `ubuntu-latest` runner and blocks downstream steps until the database is confirmed ready.

### Context

This is the second task in Phase 3 (Database Validation In CI). It builds on #29 (CLI installed) and #21 (Phase 1 pnpm scripts that wrap Supabase CLI invocations consistently). The `ubuntu-latest` runner ships with Docker, which is what `supabase start` uses internally. The step must not proceed until the Postgres port is accepting connections — premature downstream steps against a not-yet-ready DB produce intermittent flake rather than clean failure. All stdout/stderr from `supabase start` must be captured in the run log so startup failures are diagnosable without re-running.

### Files

- Modify: `.github/workflows/ci.yml` — add `supabase start` step and a readiness check step

### Acceptance Criteria

- [ ] `.github/workflows/ci.yml` has a step `name: Start local Supabase` placed after `Install dependencies` and before `Lint`, invoking `pnpm supabase start` (or equivalent pnpm script introduced by #21)
- [ ] A readiness step follows immediately: `name: Wait for Supabase DB ready` using `supabase status` in a short retry loop (e.g. `until supabase status 2>/dev/null | grep -q "DB URL"; do sleep 2; done`) with a hard timeout (e.g. 60 s via `timeout 60`)
- [ ] Both steps use `working-directory: apps/web` if `supabase/config.toml` lives there, or repo root if not — matches the project layout
- [ ] CI run logs show the Supabase service URLs (Postgres, REST, Studio) printed by `supabase start` before any test step executes
- [ ] If `supabase start` exits non-zero, the job fails immediately (no silent swallow via `|| true`)
- [ ] The existing `Lint`, `Typecheck`, and `Build` steps are unaffected; only the `Test` step gains a live DB behind it (addressed fully in #32)

### TDD Steps

The workflow file is the deliverable; the TDD cycle is validated via a real Actions run:

1. On a feature branch, add the `Start local Supabase` step without the readiness check. Push. Observe the run — it is expected to fail on a downstream step or to proceed to `Test` while the DB is still starting, producing a timing-related failure. This confirms the step executes but that a readiness gate is needed.
2. Add the `Wait for Supabase DB ready` readiness step. Push. Observe that the job now only proceeds once `supabase status` reports the DB URL.
3. Temporarily break the step (e.g. `pnpm supabase start --bad-flag`) and push. Verify the job fails at exactly `Start local Supabase` rather than silently continuing.
4. Restore the correct invocation. Push. Confirm all existing steps (`Lint`, `Typecheck`, `Test`, `Build`) still pass.
